### 1. Approved implementation direction

Prepare the minimum source changes required for:

1. Operation-local shared acquisition context.
2. Immutable input receipts at original Host consumption.
3. Dependency receipt attribution through source, Unit and Project caches.
4. Acquisition-scope construction at actual program demand.
5. Successful immutable proof sealing.
6. Recipient-specific acquisition qualification.
7. Borrowed or Arc-backed immutable unit reuse.
8. Private owner semantic compilation.
9. Existing currentness, publication and failure behavior.

Do not introduce global caching, mutable resolver sharing or persistent authority changes.

### 2. Critical proof requirements

The implementation must demonstrate that:

- Cached values retain complete consumed-input dependency receipts.
- Cache hits attribute those receipts to the current acquisition scope.
- Seeded source bytes retain supplied-owner authority.
- Disk-backed dependency authority is not fabricated from another owner's seed.
- Owner-only observations do not contaminate sibling proofs.
- Partial or failed acquisition is never exported as successful reusable proof.
- A recipient's existing private cached values are not silently overwritten.
- No complete project traversal is repeated merely to construct or qualify the proof.

A nonempty witness list is not sufficient evidence of complete acquisition authority.

### 3. Preserve the authority boundary

Do not change:

- Existing Witness truth predicates.
- Persisted witness formats.
- Source identity semantics.
- Project/config selection authority.
- Native package or resolution authority.
- Owner retirement/refusal behavior.
- Existing currentness validation.
- Batch prepublication checks.
- Publication tickets.
- Cancellation or retry policies.

If a required implementation change conflicts with these constraints, stop and return the exact conflict for owner review.

### 4. Concurrency and ownership

The shared acquisition context is owned by one executor compilation operation.

Successful immutable proofs may be shared among qualified jobs.

Do not share in-flight mutable resolver state.

Preserve worker concurrency, result ordering and panic/error isolation.

Recursive acquisition must retain its existing refusal behavior rather than deadlocking on an in-flight group.

A failed leader must not poison otherwise independent sibling compilations.

### 5. Required tracked tests

Prepare deterministic tests covering:

- Complete proof export through pre-cached Host, Unit and Project values.
- Exclusion of unrelated owner-only dependencies.
- Supplied-source versus disk-dependency authority.
- Divergent owner overlays.
- Different config, route, roots and package evidence.
- Request-directory and inherited-project context.
- Partial acquisition, failed acquisition and stale proof.
- Owner retirement and publication refusal.
- Missing-module/lower-bound semantics.
- Equivalent-group acquisition counts.
- Standalone explicit-file capture.
- Non-TypeScript jobs.
- Bootstrap, ordinary hydration and batch publication.

The architectural fitness predicate must measure actual complete-project acquisition and traversal separately from qualification, currentness and owner-specific semantic work.
