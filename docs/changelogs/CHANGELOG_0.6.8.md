## [0.6.8] - 2026-09-16

### Added

* **Session-level hydration discovery caching** — `workspace_query` hydration already declined to re-*compile* a candidate file (`WorkspaceIndex::file_map()`), but it had no memory of having already *searched* for a semantic target: every eligible call re-ran the CBM project search (including its lazy-reindex gate) and/or the full filesystem walk-and-read of the root, rediscovering the same candidates only to discard them as already compiled, so the expensive half of hydration was repeated on every identical query. Discovery *completion* is now session state (`src/mcp/discovery_cache.rs`): a `DiscoveryScope` is (provider, canonical root identity) and a completed entry is scope + discovery mode + entity name, recorded against the scope's current generation, so validity is a generation comparison and invalidation is O(1) per scope with no entry scan, eviction, TTL, or size cap. Providers are separate scopes (`Cbm` / `Filesystem`), so a CBM-completed project can never suppress the filesystem fallback its root would otherwise receive, and roots are independent (an additional root is discovered on its own). Discovery-mode equivalence was established from the implementation rather than assumed: `find_entities`, `forward_edges` and `transitive_dependencies` perform the identical declaration search and share one entry, while `reverse_edges` (inbound-reference discovery) keeps its own. Only *successful* discovery is recorded — including a successful discovery that found zero candidates — while failed, partial, still-indexing and CBM-unavailable discovery are never recorded, so a transient failure cannot be cached as absence and stays retryable. The cache stores no candidates, entities, edges, or answers: `WorkspaceIndex` remains the sole authority for query evaluation and every answer is still evaluated against the live index, with only the discovery step skipped. Invalidation reuses existing lifecycle events rather than adding a watcher, timer, or background worker: a successful `apply_edit` invalidates the edited file's root (both providers) and invalidates every scope when the path matches no configured root; an explicit `index_repository` refresh — through the single `cbm_proxy` funnel, whose documented purpose is external edits Clean-CTX cannot observe — invalidates that repository's root; and the source cache's existing mtime/size staleness path drops the whole cache when the session re-reads an externally modified file (files the session never reads remain the documented external-edit boundary). `ensure_indexed_for` is deliberately skipped on a hit: its only in-session dirty producer is `apply_edit`, whose invalidation forces rediscovery, and every other CBM consumer resolves its own indexing gate, so calling it merely to validate the cache would defeat the optimization. No caps, timeouts, TTLs, eviction, persistent or cross-session caches, background invalidation workers, single-flight/coalescing infrastructure, or parallel `WorkspaceIndex` mutation were introduced, and serial candidate compilation is unchanged (a separate follow-up). Recorded as invariant `WSC-003`. ### Changed

* **Hydration metadata on a discovery hit** — an unchanged repeated query now reports `hydration_attempted: true`, `discovery_completed: true`, the provider that completed discovery for this generation, and `candidates_discovered: 0` / `candidates_compiled: 0`; that pair is the observable cache-hit signal and no new field or telemetry contract was added. Per-project `project_coverage` keeps its existing shape (`status: "searched"`, `readiness: "ready"`) on a hit, a failed project search still reports `search_failed` while its root keeps the filesystem fallback (and `discovery_completed` continues to describe the overall pass, exactly as before), and no MCP tool schema, response field set, or `outputSchema` changed.

### Tests

* **Discovery-cache validity units** — `src/tests/mcp/discovery_cache.rs` pins lookup within a generation, provider specificity, root specificity, discovery-mode specificity, name specificity, per-root invalidation (`invalidate_root` drops both providers of one root and leaves other roots cached), whole-cache invalidation, and that invalidating an unknown root records nothing (a caller-supplied root that matches no configured root cannot grow the cache).
* **CBM-path discovery-count regressions** — `src/tests/mcp/workspace_query_8.rs` (`RED-H1`–`RED-H10`) counts real discovery invocations through the existing cfg(test) project-search injection, so "discovery did not run again" is asserted structurally rather than as "no file was recompiled": `RED-H1` an unchanged repeated `reverse_edges` keeps the count at 1 while the live index still answers, `RED-H2` the second call does not invoke discovery at all while a fresh target in the same project still does, `RED-H3` a successful zero-candidate discovery is cached, `RED-H4` a failed project search is retried and re-reported while the successful fallback for that root is *not* re-scanned (per-provider granularity), `RED-H5` `apply_edit` invalidates the edited root only, `RED-H6` a cache hit in a ready project does not suppress a still-indexing project, `RED-H7` declaration and inbound-reference discovery keep separate entries, `RED-H8` the three declaration-oriented query types share exactly one entry, `RED-H9` an explicit repository refresh forces rediscovery, and `RED-H10` three configured roots each discover exactly once across repeated calls. Every case serializes on the existing hydration test mutex and none asserts elapsed time.
* **Filesystem-fallback discovery-count regressions** — `src/tests/mcp/workspace_query_9.rs` (`RED-FS1`–`RED-FS5`) instruments the fallback scanner with a new thread-local invocation counter plus the existing `TraversalStats` file counts: `RED-FS1` a repeated query over a CBM-less root walks it once, `RED-FS2` a degraded-CBM fallback scan runs once and reports the `filesystem` provider as completed afterwards, `RED-FS3` an externally modified file detected through the source cache's mtime/size path forces rediscovery, `RED-FS4` a failed or partial scan stays retryable, and `RED-FS5` invalidating one root re-scans exactly that root (one file read, not two) while the cached root is skipped.
